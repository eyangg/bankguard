> 기준 문서: `BANKGUARD_CLAUDE_MASTER_SPEC.md` v2.0 장(V0~V9). 이 문서와 명세가 충돌하면 명세가 우선입니다.
> 수업 문서 흐름: MVP → **PRD**(이 문서) → SPEC → PLAN
> 상태 표기: **완료** = 구현·테스트됨 / **예정(Phase X)** = `docs/plan.md`의 해당 Phase에서 만들 것

## 1. 문제 정의

은행 송금 API에서 사고가 나는 지점은 대부분 **업무 규칙의 구멍**입니다.

- 남의 계좌 번호만 바꾸면 그 사람 거래내역이 보인다 (BOLA)
- 같은 잔액으로 동시에 두 번 송금하면 돈이 복제된다 (경쟁 조건)
- 네트워크가 끊겨 재전송하면 두 번 출금된다 (멱등성)
- 일반 고객이 관리자 기능을 호출할 수 있다 (BFLA)
- 요청에 `balance`를 끼워 넣으면 잔액이 바뀐다 (Mass Assignment)
- 비밀번호·토큰을 무한정 추측할 수 있다 (무차별 대입)
- 2차 인증(OTP)을 건너뛰고 송금이 실행된다

BankGuard는 이 구멍들이 **실제로 막혀 있는지를 자동으로, 반복 가능하게, 근거와 함께** 확인하는 도구입니다.

## 2. 목표와 비목표

**목표**
- 일부러 구멍을 낸 취약 버전과 고친 안전 버전에 같은 점검을 실행해 **FAIL → PASS**를 실제 응답·DB 상태로 보여 준다.
- 코드 패턴 점검(정적 분석)과 실행 점검(동적 테스트)이 **각각 무엇을 잡고 놓치는지** 데이터로 비교한다.
- 수업 필수 스택 **FastAPI · React · TypeScript · Supabase**로 동작한다.

**비목표**
- 실제 금융 서비스 수준의 인증·규제 준수·운영(실서비스 사용 불가)
- 취약 버전의 인터넷 공개
- 외부 시스템·실제 은행·타인 계정에 대한 요청

## 3. 사용자와 사용 흐름

| 사용자 | 흐름 |
|---|---|
| 고객 | 회원가입·로그인 → 내 계좌 → 거래내역 → 송금(OTP 확인) → 계좌 별칭 변경 |
| 운영자(관리자) | 로그인 → 계좌 지급정지 → **보안 점검 결과(읽기 전용)** 확인 |
| 점검 담당(개발자 본인) | CLI·CI에서 시나리오·Semgrep·pip-audit 실행 → 결과 JSON·진단 보고서 생성 |

점검 실행은 **CLI와 CI에서만** 합니다. 웹 화면은 결과를 관리자에게 읽기 전용으로만 보여 줍니다.

## 4. 기능 요구사항

### 4.1 은행 기능

| ID | 요구사항 | 상태 |
|---|---|---|
| F-01 | 내 계좌 목록 조회(원화 정수 금액) | 완료 |
| F-02 | 내 계좌 거래내역 조회, 남의 계좌는 403 | 완료 |
| F-03 | 송금: 금액은 1원 이상 정수, 잔액 초과·지급정지 계좌는 거절, 출금·입금·기록을 한 번에 처리 | 완료 |
| F-04 | 송금 멱등성: 같은 `request_id` 재전송은 한 번만 출금, 같은 ID에 다른 내용은 409 | 완료 |
| F-05 | 계좌 별칭 변경: `nickname` 외 필드가 섞이면 422 | 완료 |
| F-06 | 관리자 지급정지: 고객은 403 | 완료 |
| F-07 | 회원가입·로그인(이메일·비밀번호·이름, 비밀번호는 Argon2id 해시) | 예정(Phase C) |
| F-08 | 서버 측 세션(httpOnly·SameSite=Strict 쿠키, 유휴 30분·절대 8시간 만료, 로그아웃 폐기), CSRF 토큰 | 예정(Phase C) |
| F-09 | 송금 2차 인증: 송금 대기 생성 → 서버가 OTP(TOTP) 검증 후에만 실행, 재사용 거절, 5분 만료 | 예정(Phase C) |
| F-10 | 데이터를 Supabase PostgreSQL에 저장(브라우저는 Supabase에 직접 접속하지 않음) | 예정(Phase B) |
| F-11 | React + TypeScript 화면: 로그인·회원가입, 계좌, 거래내역, 송금+OTP, 별칭, 지급정지, 점검 결과 | 예정(Phase D) |

### 4.2 보안 점검 기능

| ID | 점검 | 판정 방법 | 상태 |
|---|---|---|---|
| SC-01 | 타인 거래내역 조회 차단 (BOLA) | 남의 계좌 조회 → 안전: 403, 데이터 미노출 | 완료 |
| SC-03 | 동시 송금 경쟁 조건 | 동시 2건 → 안전: 1건 성공·1건 거절, 잔액 합 보존 | 완료(SQLite). PostgreSQL 재현은 예정(Phase B) |
| SC-04 | 중복 송금 방지 (멱등성) | 같은 요청 2회 → 안전: 출금 1회 | 완료 |
| SC-05 | 고객의 관리자 기능 호출 차단 (BFLA) | 고객 토큰으로 지급정지 → 안전: 403, 상태 불변 | 완료 |
| SC-06 | 요청 필드 끼워넣기 차단 (Mass Assignment) | 잔액·소유자·상태 끼워넣기 → 안전: 422, DB 불변 | 완료 |
| SC-07 | 인증 무차별 대입 차단 (시도 횟수 제한) | 5회 실패 뒤 → 안전: 429, 잠금 중엔 맞는 토큰도 거절 | 완료(토큰 인증 기준). 로그인 연결·계정 기준은 예정(Phase C) |
| SC-08 | Supabase 직접 접근 차단 (설정 점검) | 모든 테이블 RLS 켜짐 + 외부 API 역할 권한 없음 | 예정(Phase B) |
| SC-09 | 2차 인증 단계 건너뛰기 차단 | OTP 없음·틀림·재사용 → 안전: 송금 미실행 | 예정(Phase C) |
| SC-02 (세부) | 잘못된 금액(0원·음수) 차단 | 안전: 422, DB 불변 | 완료 |
| SAST | Semgrep 금융 맥락 규칙 4개 | 취약 샘플 탐지, 수정 샘플 미탐지 | 완료 |
| SCA | pip-audit 의존성 취약점 점검 | 설치된 패키지의 알려진 취약점 | 완료 |
| DET-01 | 계좌 열거 의심 탐지 | 5분 안에 서로 다른 계좌 3개에서 거부/없음 → 경보 | 완료 |

## 5. 비기능 요구사항 (지켜야 하는 원칙)

| ID | 원칙 |
|---|---|
| N-01 | **안전 모드만 네트워크로 노출.** 취약 버전은 테스트 클라이언트 + 임시 SQLite 안에서만 만든다 |
| N-02 | **브라우저는 Supabase에 직접 접속하지 않는다.** Supabase 키·DB 접속 정보를 화면 코드나 `VITE_*` 변수에 두지 않는다 |
| N-03 | 모든 테이블에 RLS를 켜고 외부 API 역할(`anon`, `authenticated`)의 테이블 권한을 회수한다 |
| N-04 | 비밀값(DB 접속 정보, 암호화 키, 시연 비밀번호)은 `.env`에만 둔다 |
| N-05 | 실제로 실행하지 않은 검사를 PASS/FAIL로 보고하지 않는다 |
| N-06 | 금액은 정수(원), 소유권은 서버가 확인, 송금은 원자적 트랜잭션, 재전송은 멱등 처리 |
| N-07 | 화면 코드는 TypeScript(`.ts`/`.tsx`, strict)만 쓴다 |
| N-08 | 기본 `pytest`는 인터넷 없이 실행된다(PostgreSQL 테스트는 `-m postgres`로 따로) |
| N-09 | 오류 응답에 내부 정보(스택트레이스·경로·SQL)를 넣지 않는다 |
