# BankGuard 위협 모델 (1페이지)

> 대상: 가상 은행의 **송금·계좌 조회 API**와 그 주변(검사 엔진, 대시보드). 로컬 학습용이며 실제 금융 서비스가 아니다.
> 기준 시점: DAY 6 (2026-10-28). **이 문서는 '구현되어 검증된 것'과 '아직 없는 것'을 구분해 적는다.**
> 위험도는 프로젝트 내부 학습용 3×3(가능성 × 영향) 등급이며 CVSS 인증 점수가 아니다.

## 1. 데이터 흐름

```text
  ┌───────────────┐   ①X-Demo-Token + JSON    ┌──────────────────────┐   ③SQL(파라미터 바인딩)  ┌──────────┐
  │ 클라이언트      │ ───────────────────────▶ │ FastAPI (안전 모드만 공개) │ ─────────────────────▶ │ SQLite    │
  │ (고객 A/B/C,   │ ◀─────────────────────── │  인증 → 권한 → 검증 → 서비스 │ ◀───────────────────── │ users     │
  │  운영자)       │   ②응답 코드 + 본문        └──────────┬───────────┘                         │ accounts  │
  └───────────────┘                                      │ ④감사 로그(마스킹)                    │ transfers │
                                                         └─────────────────────────────────────▶│ audit_log │
                                                                                                └──────────┘
  ┌───────────────┐  ⑤검사 실행 버튼   ┌─────────────────────────────┐  ⑥인프로세스 요청    ┌─────────────────────────┐
  │ Streamlit      │ ───────────────▶ │ scanners (api_runner,        │ ──────────────────▶ │ 격리 앱 + 임시 폴더의 새 DB │
  │ 대시보드        │ ◀─────────────── │          sast_runner)        │ ◀────────────────── │ (취약 비교 구현은 여기서만)  │
  └───────────────┘  ⑨결과 표시         └──────────────┬──────────────┘                     └─────────────────────────┘
                                                      │ ⑦subprocess(shell=False, 고정 경로)
                                                      ▼
                                      Semgrep CE ──⑧──▶ 로컬 소스(fixtures, backend) + rules/bankguard.yml
```

**신뢰 경계**
1. 네트워크 ↔ FastAPI: 외부에서 오는 모든 입력(헤더·경로·본문)은 신뢰하지 않는다.
2. 공개 서버 ↔ 검사 전용 취약 구현: 취약 구현은 공개 경로에 존재하지 않는다(임시 폴더 DB + 인프로세스에서만 생성).
3. 대시보드/검사 엔진 ↔ 로컬 파일·프로세스: 대상 경로와 규칙 파일은 코드 상수이며 사용자 입력을 받지 않는다.

## 3. STRIDE 분석 (송금 API 중심)

| 위협 | 시나리오 | 통제 / 대응 | 상태 | 확인 방법 |
|---|---|---|---|---|
| **S** 위장 | 토큰 없이·틀린 토큰으로 호출 | 모든 보호 경로에 공통 토큰 의존성, 실패 시 401 + `AUTH_FAIL` 기록 | 구현·검증 | T04·T05, 감사 로그 테스트 |
| **S** 위장 | 토큰 무차별 대입 | 시도 횟수 제한 | **미구현**(P1 SC-07) | — |
| **T** 변조 | 요청에 금액 조작(0원·음수·소수·문자열) | `StrictInt`·범위 검증(422), DB `CHECK(amount_krw > 0)` 이중 방어 | 구현·검증 | T06·T07·T15, SC-02 |
| **T** 변조 | 요청 JSON에 잔액·소유자·상태 끼워넣기(Mass Assignment) | 허용 필드만 정의(`extra=forbid`) + 고정 UPDATE | 구현·검증 | SC-06, T22 |
| **T** 변조 | 같은 잔액으로 동시 출금(경쟁 조건) | `BEGIN IMMEDIATE` + 조건부 UPDATE로 확인·차감 원자화 | 구현·검증 | SC-03(20회 반복) |
| **T** 변조 | 같은 요청 재전송(중복 출금) | `request_id` 유일키 + `payload_fingerprint`, 재요청 200 / 내용 변경 409 | 구현·검증 | SC-04, T09·T10 |
| **R** 부인 | "내가 안 했다" / 공격 흔적 없음 | 인증 실패·권한 거부·송금 결과를 `audit_log`에 기록(토큰은 지문, 계좌번호 마스킹), 롤백돼도 거절 기록 유지 | 구현·검증 | T17 |
| **I** 정보 노출 | 타인 거래내역 조회(BOLA) | 서버가 토큰의 user_id와 계좌 소유자를 비교, 403 | 구현·검증 | SC-01, T03 |
| **I** 정보 노출 | 계좌 ID를 바꿔 가며 존재 여부 탐색(열거) | 명세 6.4에 따라 없는 계좌 404 / 남의 계좌 403으로 **구분 응답하므로 열거는 가능**하다. 완화책은 시도를 감사 로그에 남기는 것(`ACCESS_DENIED`/`NOT_FOUND`)과 탐지 규칙 | **일부 구현**: 기록은 됨, **탐지 규칙 DET-01 미구현**(DAY 7) | T17 / T18 예정 |
| **I** 정보 노출 | 서버 오류 시 스택트레이스·경로·SQL 노출 | 일반화된 오류 응답 | **미구현**(T16 예정) | — |
| **I** 정보 노출 | 로그에 토큰·전체 계좌번호 | 지문·마스킹만 저장, 로그 출력 SAST 규칙 BG-SAST-003 | 구현·검증 | T17, 규칙 테스트 |
| **D** 서비스 거부 | 대량 요청·무제한 호출 | 속도 제한 | **범위 밖**(로컬 단일 사용자 실습) | — |
| **E** 권한 상승 | 일반 고객이 관리자 기능(지급정지) 호출(BFLA) | 관리 라우터 전체에 역할 검사를 기본값으로 적용(기본 거부), 403 + 기록 | 구현·검증 | SC-05, T20 |
| **E** 권한 상승 | 취약 비교 구현이 공개 서버에 붙음 | 임시 DB 경로 강제, 지연 import, 결함 하나씩 격리, 공개 진입점은 secure 고정 | 구현·검증 | 격리 테스트 |

## 4. 정적 분석 관점의 위협

| 위협 | 통제 | 한계 |
|---|---|---|
| SQL 문자열 조립 → SQL 삽입 | 파라미터 바인딩 사용, 규칙 BG-SAST-001로 조립 패턴 탐지 | 값이 내부 상수일 때도 걸리는 **오탐** 가능, 다른 함수에서 조립해 넘기면 **미탐** |
| 금액에 float → 정밀도 오류 | 정수 금액 불변식, 규칙 BG-SAST-002 | 이름에 단서가 없는 변수는 놓침 |
| 민감정보 로그 출력 | 규칙 BG-SAST-003 | 딕셔너리 키·함수 결과는 놓침 |
| TLS 검증 해제·하드코딩 비밀 | 규칙 BG-SAST-004 | `requests` 외 클라이언트는 놓침 |
| **업무 로직 결함**(소유권·역할·동시성·멱등성·금액 검증 누락) | **정적 규칙으로 탐지하지 않는다.** 실행 기반 시나리오가 담당 | 실제로 `insecure_lab.py`에서 Semgrep이 잡은 것은 SQL 조립 1건뿐이다 |

## 5. 알려진 한계 (정직한 범위)

- 토큰은 학습용 가상 식별자이며 실제 은행 인증(다중 인증, 세션 관리, 전자서명 등)과 동등하지 않다.
- 전송 구간 암호화(TLS)는 로컬 HTTP 실습이라 적용하지 않는다.
- 같은 `request_id`를 다른 사용자가 쓰면 409로 요청 ID의 사용 여부가 간접적으로 드러날 수 있다(미조치).
- 이 문서는 구현된 통제와 테스트를 기준으로 쓴 **분석 결과**이며, 실서비스에 대한 보증이 아니다.
