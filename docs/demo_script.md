# BankGuard 시연 대본 (3분 / 5분)

> 모든 계좌·토큰은 허구의 더미 데이터이고, 시연은 로컬(127.0.0.1)에서만 동작합니다. 인터넷·외부 API가 필요 없습니다.
> 화면의 버튼·탭 이름은 `frontend/tabs.py`의 실제 문구입니다.

## 시연 전 준비 (발표 직전 1회)

```powershell
# 터미널 A — API (선택: 켜 두면 ① 개요에 실시간 잔액이 보입니다. 검사 버튼은 API 서버 없이도 동작합니다)
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
# 터미널 B — 대시보드
.\.venv\Scripts\python.exe -m streamlit run frontend/app.py
```

- 브라우저에서 http://127.0.0.1:8501 을 직접 엽니다(자동으로 열리지 않음).
- **사전 점검:** 발표 전에 한 번 `전체 검사 실행`을 눌러 오류 없이 끝나는지 확인합니다. 발표 중에 결과가 비어 보이면
  "미실행"이라는 뜻이므로 버튼을 눌러 실제로 실행하세요(실행 전 표시는 가짜 결과가 아닙니다).
- Semgrep이 설치되지 않았으면 ③탭은 "스캔 오류"로 표시됩니다(0건으로 위장하지 않음). `README.md`의 설치 절을 확인하세요.
- 스크린샷이 필요하면 아래 "캡처 체크리스트"를 따라 직접 찍어 `docs/screenshots/`에 넣으세요(이 저장소에는 아직 없음).

## 3분 시연 (핵심 흐름)

| 시간 | 화면 / 클릭 | 말할 내용 |
|---|---|---|
| 0:00–0:25 | **① 개요** 탭 | "은행 송금 API는 접근제어와 거래 무결성이 핵심입니다. 가상 고객 3명과 운영자 1명이 있는 **로컬 실습 환경**이고 실제 금융 데이터는 없습니다." |
| 0:25–1:05 | **② API 보안 테스트** → 실행 모드 **취약 버전(격리 실습)** → `보안 시나리오 실행` | "각 시나리오는 임시 DB와 새 앱에서 실제 요청을 보내고 **응답 코드와 DB 상태**로만 판정합니다. 취약 버전은 격리된 임시 환경에서만 돌고 공개 서버에는 없습니다." 결과의 ❌ FAIL(예: SC-03 동시 송금 → 둘 다 201, 잔액 합 +300,000원 복제)을 짚는다. |
| 1:05–1:40 | 실행 모드 **안전 버전(수정 후)** → `보안 시나리오 실행` | "같은 시나리오가 ✅ PASS로 바뀝니다. SC-03은 201 1건·409 1건, 잔액 합 보존. 판정 근거에 양성 대조(정상 요청은 성공)가 있어 '아무것도 안 해서 통과'가 아닙니다." |
| 1:40–2:20 | **③ 정적 코드 분석** → `Semgrep 정적 분석 실행` | "Semgrep CE와 금융 맥락 로컬 규칙 4개(SQL 조립·금액 float·민감정보 로그·TLS/비밀값)입니다. 취약 샘플은 탐지, 수정 샘플은 미탐지(패턴 없음). 결과는 **검토 필요** 의심 항목이지 확정 취약점이 아닙니다." |
| 2:20–2:50 | **④ 개선 비교·보고서** → `전체 검사 실행 (취약 → 안전 → 정적 분석 → DET-01)` | "핵심 5개 중 5개가 FAIL→PASS로 개선됐습니다. 아래 SAST↔동적 비교표를 보면 **업무 로직 결함은 Semgrep이 못 잡고** 동적 테스트만 잡습니다." |
| 2:50–3:00 | 같은 탭 하단 | "진단 보고서를 Markdown으로 내려받을 수 있고, 이 도구는 정의한 검사 범위만 확인합니다. 실서비스 보증이 아닙니다." |

## 5분 시연 (3분 + 아래 확장)

3분 흐름에 다음을 끼워 넣습니다.

1. **(1:05 직후, +40초) 시나리오 상세 한 건 보기** — FAIL/ERROR 항목은 기본으로 펼쳐져 있고 PASS 항목은 클릭해서 펼칩니다. SC-04 멱등성: "같은 request_id로 두 번 보내면 취약 버전은 새 거래로 처리해 이중 출금(기록 3건), 안전 버전은 200으로 같은 거래 ID를 돌려주고 출금은 1회입니다. 같은 ID에 금액이 다르면 409입니다."
2. **(2:20 직후, +50초) DET-01 탐지** — ④탭 `DET-01 탐지 검증 실행`: "감사 로그에는 토큰 원문이 아니라 지문, 계좌번호는 마스킹해서 남깁니다. 한 사용자가 5분 안에 서로 다른 계좌 3개에서 거부/없음 응답을 받으면 경보 1건이 생깁니다(2회까지는 무경보)." 한계도 같이 말한다: 천천히 시도하거나 토큰을 바꾸면 놓친다, **탐지이지 차단이 아니다**.
3. **(마무리, +30초) 한계와 확장** — "SC-02(금액 검증)는 세부 테스트로 두었고, 속도 제한·인증 강화는 구현하지 않았습니다(`docs/limitations.md`)."

## 예상 질문 → 답변 핵심

| 질문 | 답변 |
|---|---|
| 왜 정적 분석과 API 테스트를 같이 쓰나요? | 탐지 범위가 달라서입니다. 비교표에서 업무 로직 결함 6건은 Semgrep이 못 잡았고, SQL 조립·float 금액은 시나리오가 없어 Semgrep만 잡았습니다. |
| 취약한 코드가 서버에 노출되지 않나요? | 취약 구현은 임시 폴더 DB + 인프로세스 `TestClient`에서만 생성되고, 공개 진입점 `backend/main.py`는 안전 모드로 고정됩니다. 격리 테스트가 이를 검증합니다. |
| 동시성 결과가 매번 같나요? | SC-03은 `threading.Barrier`로 동시 시작시키고 20회 반복 테스트로 결과가 같음을 확인했습니다(테스트 하네스에서만 지연 삽입). |
| Semgrep 0건이면 안전한가요? | 아닙니다. 0건은 "그 규칙의 패턴을 못 찾았다"일 뿐이고, 스캔 오류와 구분해서 표시합니다. |
| AI는 어디에 썼나요? | README의 "AI 활용 내역과 본인이 설계·검증·수정한 부분" 절을 보세요. |

## 캡처 체크리스트 (직접 촬영)

1. ① 개요 — 가상 고객·계좌 표와 "최근 검사 실행 요약"
2. ② 취약 버전 실행 결과 (FAIL 표시와 근거)
3. ② 안전 버전 실행 결과 (PASS 표시)
4. ③ 탐지 목록 + 취약 샘플 ↔ 수정 샘플 비교표(미탐지(패턴 없음))
5. ④ 개선 비교표, SAST↔동적 비교표, DET-01 결과
6. GitHub Actions `security-check` 성공 실행 화면
