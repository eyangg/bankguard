# BankGuard MVP — 가장 작게 만들어도 가치가 있는 범위

> 기준 문서: `BANKGUARD_CLAUDE_MASTER_SPEC.md` v2.0 장(V0~V9). 이 문서와 명세가 충돌하면 명세가 우선입니다.
> 수업 문서 흐름: **MVP**(이 문서) → PRD → SPEC → PLAN

## 1. 한 줄 소개

**BankGuard는 가상의 작은 은행을 만들어 두고, 그 은행의 송금·계좌 API가 해킹 시도를 제대로 막는지 자동으로 검사해 결과를 보여 주는 보안 점검 프로젝트입니다.**

## 2. 왜 만드나

- 은행 앱에서 가장 위험한 문제는 "남의 계좌를 볼 수 있다", "같은 돈이 두 번 빠져나간다", "고객이 관리자 기능을 쓴다" 같은 **업무 규칙의 구멍**입니다.
- 이런 구멍은 코드를 훑어보는 도구(정적 분석)로는 잘 안 잡히고, **실제로 요청을 보내 봐야** 드러납니다.
- 그래서 일부러 구멍을 낸 '취약 버전'과 고친 '안전 버전'에 같은 공격을 보내고, **취약 버전은 뚫리고(FAIL) 안전 버전은 막는지(PASS)**를 실제 응답과 DB 상태로 확인합니다.
- 금융권 IT 보안 직무(취약점 진단, 시큐어코딩, DevSecOps)에서 하는 **진단 → 조치 → 이행점검** 흐름을 작게 재현하는 것이 목표입니다.

## 3. 누가 쓰나

| 사용자 | 하는 일 |
|---|---|
| 가상 고객 | 로그인해서 내 계좌·거래내역을 보고, 송금합니다 |
| 가상 운영자(관리자) | 계좌를 지급정지하고, 보안 점검 결과를 읽기 전용으로 봅니다 |
| 발표를 듣는 사람·면접관 | 점검 결과와 "왜 이렇게 설계했는지"를 봅니다 |

모든 사용자·계좌·금액은 **허구의 테스트 데이터**입니다. 실제 은행이나 외부 시스템에는 요청하지 않습니다.

## 4. MVP에 반드시 들어가는 것

1. **안전한 가상 은행 API** — 계좌 조회, 거래내역, 송금, 계좌 별칭 변경, 관리자 지급정지
2. **핵심 보안 시나리오 자동 점검** — 취약 버전 FAIL → 안전 버전 PASS를 실제로 보여 주기
3. **정적 분석(Semgrep)** — 코드에서 위험한 패턴(SQL 문자열 조립, 금액에 소수점 사용 등) 찾기
4. **두 방법 비교표** — 동적 점검과 정적 분석이 각각 무엇을 잡고 무엇을 놓치는지
5. **감사 로그와 탐지 규칙 1개** — 남의 계좌를 여기저기 찔러 보는 행동(계좌 열거)을 로그로 탐지
6. **진단 보고서** — 점검 항목, 위험도, 근거, 조치 방법, 재점검 결과를 담은 Markdown 문서
7. **CI 보안 게이트** — 코드를 올릴 때마다 자동 점검, 기준을 어기면 실패
8. **수업 필수 스택(v2.0)** — FastAPI · React · TypeScript · Supabase로 동작하는 화면과 DB

## 5. MVP에 넣지 않는 것

- 실제 계좌 개설, 실명 인증, 오픈뱅킹·결제 연동
- 취약 버전을 인터넷에 공개하는 것(취약 버전은 테스트 안에서만 만듭니다)
- 이상거래를 예측하는 AI 모델, 자체 정적 분석 엔진
- 대규모 트래픽·클라우드 운영 구조
- 확장 항목(X1~X4: CSRF·XSS 점검, 이상거래 탐지 확장, 점검 도구 고도화, 클라우드 배포) — Phase E가 끝난 뒤에만

## 7. 성공했다고 말할 수 있는 기준

- React 화면에서 로그인 → 송금(OTP) → 거래내역 확인이 되고, 데이터가 FastAPI를 거쳐 Supabase에 저장된다.
- 핵심 시나리오가 취약 버전에서는 FAIL, 안전 버전에서는 PASS로 **실제로** 나온다.
- 브라우저가 Supabase에 직접 접속하지 않는다(Network 탭 확인).
- 실행하지 못한 검사는 PASS로 세지 않고 "미검증" 또는 "SKIP"으로 표시한다.

자세한 완료 기준은 명세 V8을 따릅니다.
