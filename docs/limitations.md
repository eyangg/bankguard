# 한계와 주의사항

> BankGuard는 금융권 애플리케이션 보안 업무 흐름(시나리오 설계 → 자동 검증 → 정적 분석 → 수정 전후 비교 → 보고)을
> **학습용으로 재현한 로컬 프로젝트**입니다. 아래 한계를 알고 쓰세요. 구현되지 않은 것은 구현되었다고 쓰지 않습니다.

## 1. 실서비스에 쓸 수 없는 이유

- **인증이 실제가 아닙니다.** `X-Demo-Token`은 고정된 가상 문자열(`demo-token-a` 등)로 사용자를 식별할 뿐입니다. 비밀번호, 다중 인증, 세션 만료, 전자서명, 토큰 폐기는 없습니다.
- **전송 구간 암호화(TLS)를 쓰지 않습니다.** 로컬 HTTP(127.0.0.1) 실습입니다.
- **속도 제한이 없습니다.** 무차별 대입·대량 요청 방어(명세 P1 SC-07)는 구현하지 않았습니다.
- **금융 규제·운영 요건을 다루지 않습니다.** 전자금융 관련 법규, 이상거래탐지시스템(FDS) 수준의 탐지, 장애 복구, 감사 보존 기간 등은 범위 밖입니다.
- **DB는 SQLite 단일 파일입니다.** 다중 서버·분산 환경의 동시성(여러 DB 노드, 분산 락)은 검증하지 않았습니다. 동시 송금 검증은 단일 SQLite 파일과 한 프로세스 안의 스레드 경합입니다.
- 모든 계좌·사용자·토큰은 허구의 더미 데이터입니다. 실은행이나 제3자 시스템에 요청하지 않습니다.

## 2. 검사 범위의 한계 (동적 API 테스트)

- **정의한 시나리오만 확인합니다.** 핵심 5종(BOLA, 동시 송금, 멱등성, BFLA, Mass Assignment)과 세부 1종(금액)이며, 나머지 취약점 유형(세션 고정, SSRF, 파일 업로드 등)은 다루지 않습니다.
- **PASS는 "정의한 요청 변형에서 기준을 만족했다"는 뜻입니다.** 모든 입력 조합에서 안전하다는 증명이 아닙니다. 예: Mass Assignment는 변형 3종, 금액은 음수·0원 등 고정된 사례입니다.
- **취약 구현은 실제 사고 코드가 아니라 비교용 재현 코드입니다.** 결함 하나당 구현 하나이며 안전 코드와 결함 부분만 다르게 만들었습니다. 실제 취약점 패턴을 단순화했으므로 실제 시스템의 모양과 다를 수 있습니다. 근거 사례는 코드 주석과 `README.md`에 있습니다.
- **SC-02(금액)의 취약 구현은 별도 스키마를 씁니다.** 안전 스키마에는 `CHECK (amount_krw > 0)`이 있어 서버 검증 누락이 DB에서 가려지기 때문입니다(명세가 허용한 방식, 코드에 이유 명시).
- **경쟁 조건 재현은 테스트 하네스의 도움을 받습니다.** 비원자적 구현에서도 실제 타이밍에 따라 재현이 달라질 수 있어, `threading.Barrier`와 하네스(`scanners/race_harness.py`)로 결정적으로 만들었습니다. 지연은 취약 코드가 아니라 테스트 쪽에서 넣습니다. 20회 반복해도 결과가 같음을 테스트로 확인했지만, 이는 이 하네스 안에서의 결과입니다.
- **검사 무결성:** 응답 코드와 DB 상태로만 판정하고, 결함 때문이 아닌 오류(5xx, 예외)는 FAIL이 아니라 ERROR로 분리합니다. 양성 대조(정상 요청은 성공)가 깨지면 ERROR입니다.

## 3. 정적 분석(Semgrep)의 한계

- **결과는 확정 취약점이 아니라 '검토 필요' 의심 항목입니다.** 사람이 문맥을 보고 판단해야 합니다.
- **오탐(실제로는 안전한데 탐지):** 예) SQL 문자열 조립이 내부 상수만 쓰는 경우에도 BG-SAST-001이 걸릴 수 있습니다.
- **미탐(실제 문제인데 못 찾음):** 예) 다른 함수에서 조립해 넘긴 SQL, 이름에 단서가 없는 float 금액 변수, 딕셔너리 키·함수 결과로 우회한 로그 출력, `requests` 외 HTTP 클라이언트의 TLS 검증 해제.
- **업무 로직 결함은 이 규칙으로 탐지하지 못합니다.** 소유권 검사 누락(BOLA), 역할 검사 누락(BFLA), 경쟁 조건, 멱등성, Mass Assignment, 금액 검증 누락은 실제로 `insecure_lab.py`에 구현돼 있어도 Semgrep은 해당 결함을 잡지 못했습니다(같은 코드에서 SQL 조립 1건만 탐지). 이것이 동적 테스트를 같이 쓰는 이유입니다.
- **0건 탐지 ≠ 안전.** "그 규칙의 패턴을 찾지 못했다"는 뜻입니다. 스캔 도구 오류(미설치, 실행 실패, 시간 초과 등)는 0건과 구분해 `SCAN_ERROR`로 표시합니다.
- **규칙은 4개뿐이고 직접 작성한 학습용입니다.** 탐지/미탐지 샘플(`fixtures/code`)로 검증했지만 상용 규칙 세트를 대체하지 않습니다.
- **Semgrep CE(무료판)만 사용합니다.** 함수 간 데이터 흐름 추적 등 유료판 기능은 쓰지 않습니다.

## 4. 감사 로그 탐지(DET-01)의 한계

- **탐지이지 차단이 아닙니다.** 경보를 만들 뿐 요청을 막지 않습니다.
- **미탐:** 5분 창 밖으로 천천히 시도하거나, 토큰을 바꿔 가며 시도하면 놓칩니다.
- **오탐:** 정상 사용자가 계좌 ID를 여러 번 잘못 입력하거나 한 토큰을 여러 사람이 공유하면 경보가 날 수 있습니다.
- 임계값(5분, 계좌 3개)은 학습용 설정값이며 실제 트래픽으로 튜닝한 값이 아닙니다.
- 이 API는 없는 계좌(404)와 남의 계좌(403)를 구분해 응답하므로(명세 6.4) 계좌 열거 자체는 가능합니다. 완화책은 흔적을 남겨 탐지하는 것입니다.

## 5. 알려진 미조치 사항

- 같은 `request_id`를 다른 사용자가 쓰면 409로 요청 ID의 사용 여부가 간접적으로 드러날 수 있습니다.
- 위험도(L×I 3×3)는 프로젝트 내부 학습용 기준이며 CVSS 인증 점수가 아닙니다.
- 스크린샷은 저장소에 포함돼 있지 않습니다. 화면 육안 확인은 사람이 해야 하는 항목입니다(`docs/demo_script.md`의 캡처 체크리스트).
- 운영 환경의 Windows 10 및 macOS에서는 검증하지 않았습니다(`README.md` 검증 기록 참고).

## 6. 이 도구가 보증하는 것

"정의된 검사 범위 안에서, 실제로 실행한 결과가 이러했다"는 것까지입니다. 시스템 전체의 안전이나 모든 취약점의 제거를 보증하지 않습니다.
